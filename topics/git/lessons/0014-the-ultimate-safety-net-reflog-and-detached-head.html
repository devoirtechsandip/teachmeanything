The Ultimate Safety Net: git reflog & Detached HEAD

Never fear breaking your repo again: learn how git reflog records every single step you take, how to resurrect deleted commits and branches from the dead, and how to tame the Detached HEAD state.

1 The Secret Truth: Git Almost Never Deletes Anything!

When you run git reset --hard or delete a branch with git branch -D feat/cart, it feels like your code vanished into thin air.

It didn't! The commits and files are still sitting inside the .git/objects/ database. All you did was delete the 41-byte pointer file. Because Git maintains a private internal diary called the Reflog (Reference Log), you can pinpoint the exact commit hash and bring it right back!

2 Inspecting the Reflog Diary

Run git reflog to see a chronological journal of every time HEAD moved:

$ git reflog
e1a4b90 HEAD@{0}: reset: moving to HEAD~1 (Accidental Hard Reset!)
8b32104 HEAD@{1}: commit: feat: awesome new search bar (The "lost" commit!)
4d9e210 HEAD@{2}: checkout: moving from main to feat/search
🎉 The 1-Line Resurrection Spell

To recover that "lost" commit 8b32104 into a brand-new branch, simply run:
git switch -c recovered-search 8b32104
Instantly, Git attaches a new branch pointer to that commit and restores your files!

3 Demystifying "Detached HEAD"

If you run git checkout <commit-hash> instead of a branch name, Git displays a scary warning: "You are in 'detached HEAD' state".

All this means is: HEAD is pointing directly to a commit number instead of pointing to a branch label. Any new commits you make will not have a branch name. To keep them, simply give them a branch name: git switch -c my-saved-work!
