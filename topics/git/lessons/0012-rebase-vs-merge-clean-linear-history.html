Rebase vs Merge: The Clean Linear History Debate

Resolve the eternal developer debate: understand how git rebase lifts and replays commits to maintain a clean linear timeline, and master the Golden Rule of Rebasing.

1 Two Philosophies of Project History

The Merge Philosophy ("Historical Truth")

Every branch divergence, timeline overlap, and merge commit is preserved as an exact chronological record of reality.

Trade-off: History graphs look like messy subway maps with criss-crossing merge bubbles.

The Rebase Philosophy ("A Story Well Told")

Git history is a published book for reviewers. Feature commits are replayed cleanly on top of the latest main branch tip.

Benefit: 100% linear history. git log reads effortlessly in single straight line.

2 What git rebase Actually Does Under the Hood

When you are on feat/cart and run git rebase main:

  1. Git finds the common ancestor commit of both branches.
  2. Git temporarily saves your feature commits (C3, C4) to temporary patch files.
  3. Git resets your branch to the latest commit on main (C2).
  4. Git replays your saved commits one by one on top of C2, generating new commit hashes (C3', C4').
🚨 The Golden Rule of Rebasing

NEVER rebase commits that exist outside your local machine on a shared public branch! Because rebasing generates new commit hashes (C3'), anyone else pulling that branch will experience severe history desynchronization.
