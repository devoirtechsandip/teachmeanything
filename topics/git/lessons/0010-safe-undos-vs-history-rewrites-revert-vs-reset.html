Safe Undos vs History Rewrites: revert vs reset

Master the Git time machine: know with surgical certainty when to use non-destructive git revert on shared branches and how to operate git reset (--soft, --mixed, --hard) safely on local branches.

1 The Golden Rule of Undoing

🚨 Public History vs Local History

If commits have been pushed to GitHub/team branches: NEVER use git reset. Use git revert. It appends a new commit that cleanly inverts the bug without breaking your team's history.
If commits are strictly local on your laptop: You can safely use git reset to reshape your commits before pushing.

2 git revert: The Safe Forward-Moving Undo

Instead of traveling back in time and erasing history, git revert <commit-hash> moves forward:

* e8b912a (HEAD -> main) Revert "feat: broken-payment-gateway"
* 3f12019 feat: broken-payment-gateway (buggy commit!)
* 1a44c9b feat: user profile page

Notice that commit 3f12019 still exists in the history log, but commit e8b912a undoes all of its changes. Teammates can pull seamlessly without merge conflicts!

3 The Three Flavors of git reset

--soft

Moves HEAD back 1 commit. Leaves all files staged in the index.

Use case: "I want to re-commit with a better message or combine with new files."

--mixed (default)

Moves HEAD back 1 commit. Leaves files in working tree (unstaged).

Use case: "I want to re-organize which files get staged into which commit."

--hard

Moves HEAD back and obliterates all working edits to match target commit.

⚠️ DANGEROUS: Destroys uncommitted code completely!
