Lesson 0002 • Core Architecture

The Three Areas of Git: Working Tree, Staging Area, and History

Understand the engine behind every Git command: why Git uses an intermediate Staging Area, how files transition between states, and how to craft clean, atomic commits from the terminal.

1. The #1 Beginner Question: Why Does Git Need "git add"?

When beginners first encounter Git, they almost always ask:

"If I already saved my file in VS Code or Notepad, why can't Git just commit it? Why do I have to run git add before git commit?"

The answer is the secret to why professional developers love Git: The Staging Area gives you precision and control.

📦 Plain English Analogy: The Shipping Box

Think of your project folder like a room in your house, and a commit like mailing a parcel to a customer.

When you are working, your room might be messy. You might be writing code for a login button, tweaking CSS colors, and testing a database script. You don't want to mail your entire messy room!

Instead, you place an open cardboard shipping box in the middle of the room. That shipping box is the Staging Area (also called the Index).

When you run git add login.js, you place only the login code into the box. Then you tape the box shut and slap a label on it by running git commit -m "feat: add user login". Your commit is clean, focused, and purposeful.

2. The Three Areas (Mental Map)

Git manages your code across three distinct physical spaces on your hard drive:

1. Working Tree (Local Workspace)

The actual files on your machine that you view, create, edit, or delete in your editor. These changes are temporary and uncommitted.

Status: Untracked or Modified
2. Staging Area (The Index)

A hidden binary file (.git/index) that stores a preview of what your next commit will contain. Populated using git add.

Status: Staged
3. Git Repository (Object Database)

The permanent archive inside .git/objects/. Once you commit, Git locks the staged files into an immutable snapshot with a unique cryptographic hash (SHA). This is your official history.

Status: Committed

4. Hands-on CLI Lab: Run This on Your Computer!

Now let's build your muscle memory. Open your Mac terminal (or VS Code terminal) and follow these exact steps:

Step-by-Step Terminal Commands
  1. Create a practice sandbox folder:
    mkdir ~/git-sandbox && cd ~/git-sandbox
  2. Initialize Git:
    git init
    Notice: Git creates the hidden .git database.
  3. Check the status:
    git status
    Git tells you: "nothing to commit (create/copy files and use 'git add' to track)".
  4. Create two new files:
    echo "# My Project" > README.md
    echo "console.log('hello');" > app.js
  5. Run status again:
    git status
    Both files appear in red under "Untracked files".
  6. Stage only the README:
    git add README.md
  7. Run status again to see the magic:
    git status
    README.md is green ("Changes to be committed"), while app.js is still red ("Untracked files")!
  8. Commit the staged snapshot:
    git commit -m "docs: add initial project readme"
  9. View your permanent history:
    git log --oneline
